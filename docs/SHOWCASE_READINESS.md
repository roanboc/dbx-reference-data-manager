Four reviews were run over the repository — the truth of the FR-01..FR-47 status table, the
demo experience, the path to a real workspace, and engineering hygiene — and their findings
merged and sequenced. The rule applied throughout: **a POC does not need to be a product; it
needs to survive an hour in front of people who have never seen it.**

## Where it stands

The substance is there. The full journey works end to end in a browser — open a form, edit a
cell, save, reload, read the History tab — with no JavaScript errors, every page renders for
every persona, empty states are designed rather than blank, dark mode is complete, and the
in-app Help reads well enough to be spoken aloud. 790 tests pass in about a minute and `ruff
check` is clean.

What was genuinely weak was the demo *material* rather than the app, and the items marked
**done** below have since been fixed on this branch.

## Before production

Confirmed problems, none of which a demo will reach.

* **A save that fails part-way writes rows with no audit entry.** The Databricks backend
  MERGEs in 500-row chunks and writes the audit only after the last chunk succeeds, so a
  failure mid-import leaves the table changed and the trail empty — the one outcome the design
  exists to prevent. Write the audit per chunk and report the partial application.
* **Business-key uniqueness only holds within the rows on screen.** `_check_unique_keys`
  compares the change set against the loaded page (`RDM_MAX_ROWS`, default 5,000). On a longer
  list, a duplicate outside the page is not seen, and the append import checks no keys at all.
  Unity Catalog does not enforce `PRIMARY KEY`, so the app is the only guard: one `SELECT` of
  the affected key values before the save closes it. FR-05's wording should either be narrowed
  or made true.
* **The whole Databricks path is proven by string comparison.** Every Databricks test either
  asserts generated SQL against a fake cursor or is one of five opt-in live tests that never
  touch files, permissions, SCD2 or any `update_*` method. Deploy once to a dev workspace, run
  `scripts/bootstrap_catalog.py --apply`, then grow `tests/test_databricks_live.py` to cover
  SCD2 enable/save/disable, `add_column`/`drop_column`, a file round trip through the volume,
  and a merge and a replace import.
* **A stopped serverless warehouse breaks the app until it is restarted.** The shared backend
  is cached forever and nothing reconnects. Detect a session-level failure in `_run`, drop the
  connection and retry once.
* **Functions created by the bundle show as raw schema names under "Unassigned".**
  `resources/schemas.yml` sets `rdm.display_name` / `rdm.owner` / `rdm.domain` as schema
  properties, and both that file and DEPLOYMENT.md say the app reads them back — but the read
  path uses schema tags and the registry, never `DBPROPERTIES`. Either read them, or have the
  bootstrap script seed `_catalog.functions` from them (cheaper, and no per-schema query).
* **Raw Spark error text reaches business users.** Map the handful of error classes the app can
  actually produce to a sentence and keep the full text in the log.
* **The callback layer is untested** — 46 callbacks, every save/import/schema/SCD2/file path.
  The harness already exists: `tests/test_ui_app.py` POSTs to `/_dash-update-component`, and
  that pattern works for any callback. Also delete the claim in DESIGN.md §9 that a Playwright
  suite covers these flows; there is no such suite in the repository.
* **`ruff format` is enforced nowhere** and 11 files have drifted. Run it once, commit that
  alone, then add `ruff format --check` to CI and to `make check`.
* **`requirements.txt` says it pins minors but `~=4.4` floats the whole 4.x line.** Either
  correct the comment or pin exactly, and do one full deploy so the Apps image's pip resolution
  is proven before the showcase rather than during it.

## Deliberately not doing

* **Deploying to Databricks before the showcase**, unless the showcase itself runs on a
  workspace — see the open question below. `databricks.yml` still holds placeholder values, so
  this is a multi-day path, and the demo runs on DuckDB.
* **Building the Playwright suite DESIGN.md §9 promises.** Callback tests through the existing
  harness give the same coverage without a browser in CI. Delete the promise instead.
* **Adding a timestamp parameter to `apply_changes`** so the demo can backdate its history.
  Widening the backend contract for a demo is the wrong trade.
* **A shared upload cache and cross-process metadata invalidation.** Pin `workers = 1`; the app
  is I/O-bound on the warehouse and four threads already provide concurrency.
* **AG Grid Enterprise for multi-cell paste.** A licensing decision, and bulk update plus
  import is a defensible answer until someone asks.
* **The opt-in approval workflow.** §10 is right that it needs a product decision first; the
  storage already exists (`FormDef.settings` round-trips unknown keys), but the queue, the
  reviewer screen and the approve/reject audit are multiple days spent guessing.

## Open questions for the stakeholders

These are product calls, not engineering ones, and each changes what gets built next.

1. **Does the showcase run on the local DuckDB demo or on a live workspace?** Everything above
   assumes DuckDB, which is what is seeded and what the personas need.
2. **Per-list access inside a function.** Roles are held on the function only, so there is no
   way to let a group edit one list but not its neighbours; the workaround is a separate
   function. A SharePoint audience will ask.
3. **Change notifications.** "Alert me when this list changes" has no equivalent. A job over
   `_catalog.change_log` would be days, not weeks — but only if it is wanted.
4. **Is FR-05 an unqualified guarantee or a POC-level one?** See "before production" above.
5. **Opt-in approval per form or file** (FR-23, revived in §10).
6. **What "archived" means for a retired function**, before the retire-function wizard can be
   specified.
